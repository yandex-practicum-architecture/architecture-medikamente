## Задание 3. Оценка Data Encryption at Rest and In Transit  

**Цель:** Разработать комплексную стратегию защиты данных для системы "Медикаменте", обеспечивающую конфиденциальность и целостность данных как в состоянии покоя (at rest), так и во время передачи (in transit). Стратегия включает классификацию данных, обоснование необходимости защиты, выбор инструментов защиты, автоматизированный контроль и реестр программных и аппаратных средств, ориентированную на российскую практику и законодательство.  

### Ключевые принципы:  

**• Минимизация и псевдонимизация:** Ограничение сбора и хранения данных, использование псевдонимов вместо реальных идентификаторов, где это возможно (например, замена ФИО на уникальный ID пациента).  
**• Защита в транзите:** Обязательное использование TLS 1.2+ (рекомендуется TLS 1.3) для шифрования данных при передаче, mutual TLS (mTLS) для взаимодействия сервисов.  
**• Разделение зон и обязанностей:** Разделение прав доступа и ответственности за данные и ключи шифрования.  
**• Шифрование данных:** Использование шифрования как основного механизма защиты данных в покое и при передаче.  
**• Комплексный подход:** Внедрение многоуровневой защиты, охватывающей все этапы жизненного цикла данных.  
**• Регулярный аудит и обновление:** Пересмотр и актуализация стратегии защиты в соответствии с меняющимися угрозами и нормативными требованиями (ФЗ-152, ФЗ-323).  

### Шаг 1: Определение данных для защиты (Классификация данных)

На основе анализа информации о компании "Медикаменте", определим категории данных, требующие защиты:

• **Персональные данные (ПДн, PII):**  
  • ФИО  
  • Дата рождения  
  • Адрес  
  • Номер телефона  
  • Адрес электронной почты  
  • Данные паспорта (при необходимости)  
  • СНИЛС  

• **Медицинские данные (PHI):**  
  • Медицинская история  
  • Диагнозы  
  • Результаты анализов и исследований  
  • Назначения и рекомендации врачей  
  • Информация о госпитализациях и операциях  
  • Страховая информация  

• **Финансовые данные:**  
  • Данные банковских карт (при оплате онлайн)  
  • Информация о платежах и счетах  
  • Информация о ККМ (если применимо)  

• **Данные для аутентификации:**  
  • Имена пользователей  
  • Пароли (в зашифрованном виде)  
  • Данные для многофакторной аутентификации (MFA)  

• **Логи системы и журналы аудита:**  
  • Информация о действиях пользователей в системе  
  • Записи о доступе к данным  
  • События безопасности  

• **Legacy-файлы:**  
  • Excel-файлы, содержащие медицинские данные  
  • PDF-документы с результатами исследований  
  • Файлы 1С с финансовой информацией  

• **Коммерческая тайна / Интеллектуальная собственность:**  
  • Бизнес-планы  
  • Стратегии развития  
  • Базы данных клиентов (не ПДн, а клиентские сегменты)  
  • Уникальные методики лечения (если есть)  
  • Архитектура системы, исходный код.  

### Шаг 2: Классификация данных

Для выбора наиболее эффективных методов защиты необходимо классифицировать данные по следующим параметрам:  

• **Состояние:**  
  • **At Rest (в состоянии покоя):** Данные, хранящиеся в базах данных, файлах, на серверах и других носителях.  
  • **In Transit (во время передачи):** Данные, передаваемые по сети между компонентами системы (например, между порталом пациента и сервером ЭМК).  

• **Чувствительность:**  
  • **Критически важные:** Данные, утечка которых может привести к серьезным финансовым потерям, репутационным рискам и юридическим последствиям (финансовые данные, медицинские данные, данные для аутентификации).  
  • **Конфиденциальные:** Данные, утечка которых может нанести ущерб компании и пациентам (персональные данные, логи системы, коммерческая тайна).  
  • **Общедоступные:** Данные, которые не требуют специальной защиты (публичная информация о медицинском центре).  

• **Профиль риска:**  
  • **Высокий:** Данные, наиболее подверженные риску утечки или несанкционированного доступа (данные, хранящиеся в файлах на общем диске, данные, передаваемые по незащищенным каналам связи).  
  • **Средний:** Данные, имеющие средний уровень риска.  
  • **Низкий:** Данные, имеющие низкий уровень риска.  

• **Соответствие нормативным требованиям:**  
  • Данные, подпадающие под действие 152-ФЗ (Закон о персональных данных РФ).  
  • Данные, подпадающие под действие 323-ФЗ (Основы охраны здоровья граждан).  
  • Данные, подпадающие под действие GDPR (если применимо - например, работа с иностранными гражданами).  
  • Данные, подпадающие под действие PCI DSS (если обрабатываются данные банковских карт).

### Шаг 5: Автоматизированный контроль

**• DLP (Data Loss Prevention) системы:** Обнаружение и предотвращение утечек конфиденциальных данных (InfoWatch Traffic Monitor, Symantec DLP, Forcepoint DLP, Microsoft Purview).  
**• SIEM (Security Information and Event Management) системы:** Сбор и анализ событий безопасности для обнаружения угроз и инцидентов (Elastic/Wazuh/Splunk, MaxPatrol SIEM). Использование корреляционных правил, разработанных с учетом специфики медицинской отрасли и актуальных угроз.  
**• IDS/IPS (Intrusion Detection/Prevention Systems):** Обнаружение и блокирование атак на систему (Suricata / Snort, PT Application Firewall).  
**• Vulnerability Scanners:** Сканирование системы на наличие уязвимостей (Nessus, OpenVAS).  
**• File Integrity Monitoring (FIM):** Контроль целостности файлов для обнаружения несанкционированных изменений (AIDE, OSSEC, Tripwire).  
**• Data Discovery / Classification Scanner:** Автоматический поиск PII/PHI/SPI в legacy файлах и БД (BigID, Microsoft Purview, Apache Tika + regex). Интеграция с DLP для автоматической блокировки передачи обнаруженных конфиденциальных данных.  
**• Audit Service:** Неизменяемый (append-only, WORM) реестр всех доступов к SPI, интеграция с регистром обработки ПДн (при наличии).  
**• UEBA (User and Entity Behavior Analytics):** Анализ поведения пользователей для выявления аномалий и потенциальных инсайдерских угроз.

### Шаг 7: Политики Ключей и Параметры Шифрования

**• Алгоритмы:** AES-256-GCM для симметричного шифрования; ГОСТ 34.12-2015 как альтернатива; RSA/ECDSA для асимметричных операций/подписей. Использовать PFS (ECDHE).  
**• Формат ключей:** Master-KEK (HSM) RSA-4096 или AES-KEK, Data-Keys AES-256.  
**• Ротация:** Data-Keys – каждые 30–90 дней; Master-Key – 1 год (или по регламенту), автоматизированная смена и zero-downtime через HSM/Vault.  
**• Журналирование:** Все операции шифрования/дешифрования фиксировать в audit_service и SIEM.

•  Определение ответственных за безопасность данных и контроль доступа к ним.
